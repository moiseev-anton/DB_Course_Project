# ScooterRental

Учебное веб-приложение для аренды электросамокатов, разработанное в рамках курса по базам данных.

Цель проекта — на практике пройти путь от проектирования реляционной модели до приложения, которое работает с данными: хранит пользователей, самокаты, тарифы, аренды и платежи, выполняет связанные операции в транзакциях и строит аналитические отчёты. Помимо работы с БД, в проекте я практиковал разделение backend-приложения на слои и использование паттернов Repository и Unit of Work.

## Возможности

- Регистрация и вход по номеру телефона и паролю.
- Личный кабинет: просмотр и редактирование профиля, смена пароля.
- Каталог доступных самокатов с фильтрацией по локации и уровню заряда.
- Просмотр самоката, его местоположения и тарифа.
- Оформление аренды с расчётом длительности и стоимости по тарифу.
- Учебный сценарий оплаты, отмена аренды, просмотр текущей аренды и истории поездок.
- Аналитика для администратора за выбранный период: количество аренд, средняя длительность, доход по дням, распределение по статусам и статистика использования самокатов.

Оплата моделируется внутри приложения: создаётся запись в таблице платежей и активируется аренда. Интеграции с платёжным провайдером и реальными самокатами нет.

## Работа с базой данных

В основе приложения — шесть связанных сущностей:

| Сущность | Какие данные хранит |
| --- | --- |
| `User` | Профиль пользователя, уникальный номер телефона, хеш пароля и роль. |
| `Scooter` | Модель, уникальный серийный номер, статус, заряд, ссылки на локацию и тариф. |
| `Location` | Адрес и географические координаты. |
| `Tariff` | Стоимость и единицу времени для расчёта аренды. |
| `Rental` | Пользователя и самокат, длительность, время окончания, стоимость и статус аренды. |
| `Payment` | Платёж по аренде, сумму и время оплаты. |

У пользователя и самоката может быть несколько аренд; одна локация и один тариф могут относиться к нескольким самокатам. Платёж связан с арендой внешним ключом с ограничением уникальности.

В рамках проекта я работал с:

- **Проектированием связей и ограничений:** первичные и внешние ключи, `UNIQUE`, `NOT NULL`, поведение `ON DELETE SET NULL`.
- **Типами данных PostgreSQL:** `UUID` для пользователей, `Numeric` для денежных сумм, `Interval` для длительности, перечислениями для ролей и статусов.
- **SQLAlchemy ORM и SQL-выражениями:** `select`, `insert`, `update`, `delete`, `returning`, фильтрацией и сортировкой.
- **Загрузкой связанных данных:** `relationship` и `joinedload` для получения самокатов вместе с тарифами и локациями, а аренд — с самокатами.
- **Агрегатными запросами:** `JOIN`, `GROUP BY`, `COUNT`, `SUM`, `AVG`, `COALESCE` и выборками за период для отчётов.
- **Транзакциями:** объединением связанных изменений в одну операцию с явными `commit` и `rollback`.
- **Настройкой Alembic:** подключением метаданных моделей для автогенерации миграций и отдельного синхронного соединения для их выполнения.

## Архитектура и паттерны

Приложение разделено на слои:

```text
HTTP-запрос → Router → Service → Unit of Work → Repository → PostgreSQL
                ↕         ↕                         ↕
          HTML-шаблоны  Pydantic-схемы          SQLAlchemy-модели
```

### Repository

Репозитории инкапсулируют доступ к данным. Общий `SQLAlchemyRepository` реализует CRUD-операции, а репозитории пользователей, самокатов, аренд, платежей и локаций дополняют его запросами своей предметной области. Например, репозиторий самокатов выбирает доступные модели с фильтрами, а репозиторий аренд рассчитывает статистику.

Абстрактный репозиторий задаёт общий контракт, а обобщённые типы связывают конкретный репозиторий с его моделью и типом идентификатора.

### Unit of Work (UoW)

`UnitOfWork` управляет общей асинхронной сессией и набором репозиториев. Сервис открывает рабочий контекст через `async with uow`, выполняет операции и явно вызывает `commit()`. При выходе выполняются откат незакоммиченных изменений и закрытие сессии.

Пример применения — оплата аренды: создание платежа и перевод аренды в активное состояние выполняются в одной транзакции. Так связанные изменения фиксируются вместе.

### Service Layer

Сервисы содержат прикладную логику: проверку доступности самоката, расчёт стоимости аренды, обработку оплаты и подготовку отчётов. Роутеры принимают HTTP-запросы, вызывают сервисы и формируют ответы или HTML-страницы.

### Dependency Injection

FastAPI передаёт сервисы, Unit of Work, данные форм и текущего пользователя через `Depends` и `Annotated`. Зависимости объявлены отдельно в `src/dependencies.py`; сервисы принимают контракт `IUnitOfWork`.

### Схемы данных / DTO

Pydantic-схемы описывают данные для регистрации, изменения профиля, оформления аренды и отображения отчётов. Они отделяют формат данных приложения от ORM-моделей и выполняют валидацию, например проверку формата телефона и совпадения паролей.

### Middleware и доступ по ролям

Middleware загружает пользователя из сессии и добавляет его в контекст запроса. Зависимости `auth_required` и `admin_required` проверяют авторизацию и роль пользователя. Для административной аналитики требуется роль `ADMIN`.

## Окружение и состояние проекта

Проект завершён как учебная работа для практики проектирования БД и backend-разработки. Дальнейшее развитие не планируется. Репозиторий сохранён как демонстрация реализованных сценариев и архитектурных подходов; полноценное развёртывание требует отдельной подготовки схемы БД и исходных данных.

Настройки задаются через `.env` в корне проекта: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_HOST`, `POSTGRES_PORT` и `SECRET_KEY` для подписи сессий.

В Docker Compose настроены PostgreSQL 16 и приложение: порт БД на хосте — `5434`, порт приложения — `8020`. Внутри Docker-сети БД доступна по имени `rentaldb` и порту `5432`. Исходники приложения подключаются в контейнер через bind mount.

В репозитории сохранена конфигурация Alembic, но файлы ревизий миграций исключены через `.gitignore`. Поэтому клонирование репозитория не включает готовую историю создания схемы БД, а запуск контейнеров сам по себе не подготавливает таблицы и исходные данные.
